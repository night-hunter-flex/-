# 多 Agent 协作

先建立单 Agent 或固定工作流基线，再测试拆分是否改善验收结果。本文给出本库的工程建议；模式可参考 [CrewAI Crews/Flows](https://github.com/crewAIInc/crewAI)、[Microsoft Agent Framework](https://github.com/microsoft/agent-framework)与[OpenAI 官方编排说明](https://developers.openai.com/api/docs/guides/agents/orchestration)。核验日期：2026-10-10。

## 三种组织方式

| 方式 | 谁拥有下一步控制权 | 可以解决的问题 | 新增负担 |
| --- | --- | --- | --- |
| 管理者委派 | 管理者接收子任务结果并汇总 | 拆分独立任务或隔离专长 | 子任务契约、重复工作、汇总失真 |
| Handoff 交接 | 接收方接管当前分支 | 将对话交给具体专长 | 交接上下文、权限、终止条件 |
| 固定协作流程 | 程序控制顺序、分支与验收 | 明确的提取、核验、产出流程 | 状态传递和失败恢复 |

并行只适用于相互独立的工作。有依赖的查询与写入应按依赖顺序执行；同时修改同一文件前明确所有权或使用隔离工作区。

## 子任务交接契约

建议至少携带：

- 子任务目标、完成条件与允许范围。
- 相关输入及证据位置；明确哪些是原始资料、哪些是摘要。
- 工具权限与共享的预算上限。
- 输出结构、产物路径、失败状态和未解决问题。
- 谁负责最终验收与外部提交。

公开网页、论文、邮件或其他 Agent 的输出都不能自行扩大用户授权。权限应由可信应用层执行。

## 汇总与复核

管理者核对证据与产物，再形成最终结果。两个 Agent 同意同一个结论，不等于两条独立证据；共享输入、模型和先前回答都可能造成相关错误。

若研究不同方案，分别提交假设、来源和失败案例，再比较。若实现代码，先界定文件所有权，再合并与运行测试。不要把“有人复核过”替代为可查的验收记录。

## 如何判断拆分是否值得

对同一任务集固定模型、工具、数据和**总预算**，比较：

| 维度 | 记录方式 |
| --- | --- |
| 质量 | 任务成功率、证据支持率、原始失败案例 |
| 资源 | 所有 Agent 合计的模型/工具调用、token 与成本 |
| 延迟 | 端到端耗时及并行度，而非只看单个工作者 |
| 协调 | 交接次数、重复工作、冲突与汇总修正 |
| 隔离 | 不同身份、上下文、文件与权限是否明确 |

可分别试“单 Agent”“管理者 + 一个专长”“两个独立专长并行”。数量是实验设计选择，不能直接推导质量收益。
